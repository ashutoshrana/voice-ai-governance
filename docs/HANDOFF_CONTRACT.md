# Handoff publication and connection contract

Run from this checkout with Python 3.9+:

```sh
python -m pip install -e '.[dev]'
python examples/handoff_contract.py
python -m pytest tests/test_handoff_contract.py -q
```

The command prints JSON for twelve named scenarios. It calls the real
`LiveKitWarmTransferAdapter.transfer` against an in-memory room transport. The
harness temporarily patches only the optional SDK availability flag so no LiveKit
installation, credentials, model, outbound call, or network connection is needed.
This is a synthetic adapter contract test, not live SDK integration evidence.

## What the demo checks

| Event | Expected observation |
|---|---|
| Packet submitted, no connection receipt | Caller stays present; state stays active |
| Synthetic connected receipt for the current attempt/session/recipient | One local completion effect; transferred status |
| Human refuses or is unavailable | No completion; caller remains present |
| Empty participant list, publication error, cancellation | No packet recorded, no disconnect, late receipt ignored |
| Duplicate connected receipt | One completion effect |
| Caller hangs up before receipt | Caller absent; late receipt cannot complete the attempt |
| Late receipt after unavailable result | No completion |
| Receipt for another attempt or recipient | No completion |

Every submitted packet targets only `synthetic-reviewer`, even though a bystander
is present. `assert_contract` checks state immediately after publication as well
as the final outcome. A negative-control test deliberately modifies the adapter
to mark a session transferred after packet submission; the contract detects it.
The example reuses the existing state manager and PII scrubber but does not measure
PII detection recall, calibrate confidence, or demonstrate privacy compliance.

`ReceiptFixture` is intentionally a small, single-process assertion fixture.
Its receipts are generated by the test scenario; they are **not authenticated
provider events**. Do not accept a similarly shaped client JSON object as evidence
of a real connection. The fixture has no durable event log, multi-worker deduplication,
provider signature validation, timeout scheduler, or restart recovery. Real
applications own those controls and must bind provider events to the authorized
attempt, session and recipient. Publication failure and cancellation here model
local outcomes, not proof a real network delivered no bytes.

## Native LiveKit boundary (documentation reviewed 2026-09-20)

LiveKit documents a Python beta `WarmTransferTask` that handles the consultation
and call connection. Its API source sets `WarmTransferResult` after `_merge_calls()`
and exposes refusal and ringing-timeout outcomes. This is the appropriate native
orchestration boundary to investigate; successful `publish_data` is not its result.
See the [official workflow](https://docs.livekit.io/telephony/features/transfers/warm/)
and [Python API/source](https://docs.livekit.io/reference/python/livekit/agents/beta/workflows/warm_transfer.html).

There is no generic drop-in native wrapper in this example. The task uses a private
consultation room and provider-managed participant identities, whereas this adapter
requires a selected recipient already present in the publication room. Merely
calling these APIs consecutively does not bind their rooms, identities, context
exposure, acknowledgments, or cancellation outcomes. Reliable data packets also
have delivery limits; see [LiveKit's packet contract](https://docs.livekit.io/transport/data/packets/).

Before a native integration, pin an exact SDK version, inspect that version's
`WarmTransferTask` result/error contract, and test consultation-room recipient
selection and minimum-necessary context. Map only verified connection outcomes to
application state; handle refusal, timeout, caller departure, and late events
without declaring success. The repository's dependency lower bound is not evidence
that every later beta SDK version has been tested. No native SDK version or live
telephony deployment was tested by this demo, so no executable native recipe or
cross-version support claim is provided.
